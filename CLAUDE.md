# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

A QR code based product information system. An admin manages products in a web panel and prints QR codes. Customers scan a QR code and see a mobile product page (price, stock, SKT/TETT expiry info, an optional expiry-based discount).

Hobby / portfolio project, meant to be downloaded and run on a local network by whoever sets it up with their own Firebase project. It is not deployed anywhere.

## Principles

- **Vanilla JS, no framework, no build step.** Plain ES modules served as static files. Do not introduce a bundler or a framework.
- **No runtime dependencies in `package.json`.** `package.json` only holds dev tooling (Firebase emulators, tests, lint).
- **Firebase** (Firestore, Storage, Authentication) is the only backend. No custom server.
- Keep the code simple and readable. Prefer small pure functions that can be unit tested over logic buried in DOM handlers.
- Security first: never inject data into `innerHTML` without escaping; prefer `textContent`. Validate in the Firestore/Storage rules, not only in the form.

## Languages

- User interface: **Turkish and English**, chosen by the user with a TR/EN switch (see "Translations" below).
- Code, comments, commit messages, README, this file: **English**.

## Layout

```
admin/      admin panel: admin_script.js only wires modules (auth-ui, product-list, product-form, qr-modal);
            firebase-admin.js (Auth/Storage), product-images, image-convert (shrinks photos before upload), site-settings (Firestore settings/site), toast,
            upload/username helpers, list-logic, qr-logic and image-logic (pure), qr.js (wrapper)
product/    customer-facing product page
shared/     code used by both pages (Firebase app + Firestore init, config, safe DOM helpers,
            product-logic.js = pure date/stock/discount/price logic, store-config.js = discount and stock settings,
            i18n.js / i18n-core.js / i18n-init.js + locales/tr.js, en.js = the TR/EN texts)
assets/     vendored CSS/JS (Bootstrap, Bootstrap Icons, js/vendor/easyqrcodejs.js) and the page stylesheets
            css/admin.css and css/product.css (each page loads only its own)
tests/      node:test suites (security rules via the emulators, pure helpers)
e2e/        Playwright browser tests (they start the emulators; support.js has the shared helpers)
scripts/    development helpers (emulator seed, emulator-config.js = the guard that keeps scripts off real Firebase projects, screenshots.js)
docs/       README screenshots (generated by `npm run screenshots`; do not edit by hand)
.github/    CI workflow (lint, format check, npm test, browser tests) and Dependabot for the Actions
eslint.config.js, .prettierrc.json, playwright.config.js   tooling settings
firestore.rules, storage.rules   security rules (the admin is identified by a UID constant)
```

No inline scripts or inline event handlers (`onclick=` etc.): both HTML files carry a Content Security Policy `<meta>` tag (`script-src 'self' https://www.gstatic.com`). Attach events with `addEventListener`. If you add another script host, update the tag in **both** pages. Third-party libraries are vendored under `assets/js/vendor/` (see its README), not loaded from CDNs; the Firebase SDK is the one exception.

Accessibility conventions (a scan with axe-core found 0 problems on every screen after phase 4b-1; keep it that way):

- Every form control has a `<label>`; use Bootstrap's `visually-hidden` label when the design shows only a placeholder. Group radios in a `<fieldset><legend>`.
- Icon-only buttons get an `aria-label`; decorative icons get `aria-hidden="true"`.
- Each page has one `<main>` and one visible `<h1>`; keep heading levels in order (use the `.h4` etc. classes to keep the look).
- Dialogs: `role="dialog"`, `aria-modal`, a name from their title; focus moves in, Tab stays inside, Escape or a click outside closes, the page behind is `inert`, focus returns to the opener (see `admin/qr-modal.js`).
- Text needs 4.5:1 contrast. The Bootstrap blue and red are too dark/light on this theme, so the admin prices and the customer warning use lighter/darker shades (see the comments in `admin.css` and `product.css`).
- Success messages are toasts (`admin/toast.js`, a polite live region); problems stay in the alert box next to what failed.

Translations: every visible text lives in `shared/locales/tr.js` and `en.js` (flat dictionaries, same keys; `{name}` marks a filled-in value, `key.one` is the singular form). Never write a user-visible string in the code:

- Static text in the HTML: `data-i18n="key"` (also `data-i18n-placeholder|aria-label|title|alt`). The Turkish text stays in the HTML as a fallback.
- Text built in JS: `t("key", params)`; text with a badge or bold part: `tParts` (returns strings and DOM nodes, so nothing goes through `innerHTML`). Redraw what you built yourself with `onLanguageChange(callback)`.
- Pure helpers return translation keys (for example `validateExpiryDate` returns `"error.date.pastSkt"`), never sentences; the caller calls `t()`.
- Prices and dates are formatted per language (`formatPrice`, `formatDate`). Stored values stay Turkish (the category names); `categoryKey()` maps them to labels.
- `tests/i18n.test.js` fails when the dictionaries differ, an English text contains Turkish letters, a used key is missing, or a key is never used.
- The language is saved in `localStorage` (guarded; it can be unavailable) and `shared/i18n-init.js` applies it before the page is shown (`i18n-pending` class).

The Firebase SDK is loaded from Google's CDN at a fixed version (the `gstatic.com/firebasejs/<version>/` URLs in `shared/firebase.js` and `admin/firebase-admin.js`). That version must equal the `firebase` dev dependency in `package.json`; `tests/sdk-version.test.js` fails when they drift apart, so update them together. The project is on Firebase 13.x. Its test helper `@firebase/rules-unit-testing` 6 declares Node 24.12 or newer, so `engines` says `>=24.12.0` (the web pages themselves need no Node).

The customer page must not import Auth or Storage: it only loads `shared/firebase.js` (app + Firestore). Admin-only Firebase services live in `admin/firebase-admin.js`.

Existing HTML/JS files use CRLF line endings; keep them that way so diffs stay small. New files use LF.

`shared/firebase-config.js` is git-ignored. It is created by copying `shared/firebase-config.example.js`. Never commit real project settings.

## Commands

```bash
npm install            # dev tooling only (firebase-tools, rules testing)
npm run emulators      # Firestore, Storage, Auth and a static server on http://localhost:5000
npm run seed           # (emulators running) creates the dev admin: username admin / password admin123
npm test               # starts the Firestore + Storage emulators and runs tests/*.test.js
npm run test:unit      # only the pure unit tests (helpers, product logic in 4 time zones), no emulator needed
npm run test:e2e       # Playwright browser tests in e2e/ (starts the emulators itself; needs the real CDN)
npm run screenshots    # regenerates docs/screenshots/*.png for the README (starts the emulators itself)
npm run lint           # ESLint
npm run format         # Prettier (npm run format:check only checks)
```

Before every push run `npm run lint`, `npm run format:check`, `npm test` and `npm run test:e2e`: CI runs the same four and a red CI blocks the merge.

Code quality conventions:

- ESLint (`eslint.config.js`) forbids assigning HTML strings (`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`); build elements with `el()` from `shared/dom.js` or use `textContent`. Do not silence a rule with a comment to get past it; fix the code or discuss the rule with the owner.
- Prettier (`.prettierrc.json`: 4 spaces, 120 columns, no trailing commas, `endOfLine: auto` so each file keeps its CRLF or LF) formats the JavaScript and `assets/css/admin.css` / `product.css`. HTML, Markdown, JSON and the vendored files are left alone.
- Browser tests: import `test` and `expect` from `e2e/support.js` (it fails every test on uncaught page errors and CSP violations), empty the data with `clearData()` first, fix the date with `page.clock.setFixedTime(NOW)` when texts depend on it, and prefer role/label locators. A new screen or dialog needs an axe check in `e2e/accessibility.spec.js`. Scan with `accessibilityViolations()` from `e2e/support.js`, which switches transitions off first: a scan that lands halfway through a hover transition sees blended colours and reports a contrast problem that does not exist (this made CI fail now and then while local runs passed). `e2e/global-setup.js` refuses to run when `shared/firebase-config.js` does not point at the emulators.

To develop without a real Firebase project, copy the example config, set `projectId` to `demo-qr-product-info` and `useEmulator = true`. Then open `http://localhost:5000/admin/admin.html`. Emulator data is in-memory and lost on restart (run `npm run seed` again).

The admin is identified by the UID constant in `firestore.rules` / `storage.rules` (default `dev-admin-uid`, which only the emulator seed can create). Keep the two files in sync.

## Environment caveat

The cloud sandbox's default Node is 22. Install Node 24 for a session without touching the system: `npm install --no-save node@24` and put `node_modules/node/bin` first on `PATH`. The tests also pass on Node 22 (npm only warns), but 24 is the supported one.

The sandbox already has Chromium and Playwright installed (`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`): do not run `playwright install` there. The project's `@playwright/test` version is pinned to the one preinstalled in the sandbox; keep them equal when updating. `npm run test:e2e` leaves no emulator behind (`gracefulShutdown`), but if one ever does, stop it by process id (a `pkill -f firebase` also kills the shell).

Whether the sandbox can reach `www.gstatic.com` (Firebase SDK) depends on the environment's network access setting. With full access, browser checks can use the real CDN (Playwright against the emulators, no interception). With limited access the CDN is blocked: pure logic and the rules (via the emulator) can still be tested directly, and for a real-browser check bundle the `firebase` npm package with esbuild in a scratch folder and let Playwright serve it for the blocked URLs with `context.route` (every `gstatic` URL can re-export one single bundle so there is only one SDK instance). Keep any such scratch setup out of the repository.
