# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

A QR code based product information system. An admin manages products in a web panel and prints QR codes. Customers scan a QR code and see a mobile product page (price, stock, SKT/TETT expiry info, an optional expiry-based discount).

Hobby / portfolio project, meant to be downloaded and run on a local network by whoever sets it up with their own Firebase project. It is not deployed anywhere.

## Principles

- **Vanilla JS, no framework, no build step.** Plain ES modules served as static files. Do not introduce a bundler or a framework.
- **No runtime dependencies in `package.json`.** `package.json` only holds dev tooling (Firebase emulators, tests, lint).
- **Firebase** (Firestore, Storage, Authentication) is the only backend. No custom server.
- Keep the code simple and readable. Prefer small pure functions that can be unit tested over logic buried in DOM handlers.
- Security first: never inject data into `innerHTML` without escaping; prefer `textContent`. Validate in the Firestore/Storage rules, not only in the form.

## Git conventions

- Commit messages are in English, imperative mood, with a short summary line and a body that explains why.
- Do not add `Co-Authored-By`, `Assisted-by`, `Claude-Session` or any other attribution trailers, session links or "generated with" lines to commit messages or pull request descriptions. The use of Claude Code is disclosed in the README instead.
- Commits are authored as the project owner, not as Claude. The cloud sandbox's git identity is "Claude", so at the start of a session run: `git config --local user.name Cosmosprey`, `git config --local user.email 74148345+Cosmosprey@users.noreply.github.com` and `git config --local commit.gpgsign false`.
- One branch per roadmap phase (`phase-1-security`, ...), created from an up-to-date `main`. Push the branch when the phase is done.
- Do not open pull requests. The GitHub integration appends a "Generated by Claude Code" footer with a session link to anything it posts. Instead, give the owner the PR title and description as text and let them open the PR in the GitHub UI.

## Layout

```
admin/      admin panel (admin.html, admin_script.js, Auth/Storage setup, upload and username helpers, QR wrapper)
product/    customer-facing product page
shared/     code used by both pages (Firebase app + Firestore init, config, safe DOM helpers)
assets/     vendored CSS/JS (Bootstrap, Bootstrap Icons)
tests/      node:test suites (security rules via the emulators, pure helpers)
scripts/    development helpers (emulator seed)
firestore.rules, storage.rules   security rules (the admin is identified by a UID constant)
```

The customer page must not import Auth or Storage: it only loads `shared/firebase.js` (app + Firestore). Admin-only Firebase services live in `admin/firebase-admin.js`.

Existing HTML/JS files use CRLF line endings; keep them that way so diffs stay small. New files use LF.

`shared/firebase-config.js` is git-ignored. It is created by copying `shared/firebase-config.example.js`. Never commit real project settings.

## Commands

```bash
npm install            # dev tooling only (firebase-tools, rules testing)
npm run emulators      # Firestore, Storage, Auth and a static server on http://localhost:5000
npm run seed           # (emulators running) creates the dev admin: username admin / password admin123
npm test               # starts the Firestore + Storage emulators and runs tests/*.test.js
npm run test:unit      # only the pure unit tests, no emulator needed
```

To develop without a real Firebase project, copy the example config, set `projectId` to `demo-qr-product-info` and `useEmulator = true`. Then open `http://localhost:5000/admin/admin.html`. Emulator data is in-memory and lost on restart (run `npm run seed` again).

The admin is identified by the UID constant in `firestore.rules` / `storage.rules` (default `dev-admin-uid`, which only the emulator seed can create). Keep the two files in sync.

## Environment caveat

In the Claude Code cloud sandbox, `www.gstatic.com` (Firebase SDK) and `cdn.jsdelivr.net` (QR library) are blocked by the network policy. Pure logic (date, stock, discount) and Firestore/Storage rules (via the emulator) can be tested directly. For a real-browser check in the sandbox, bundle the `firebase` and `easyqrcodejs` npm packages with esbuild in a scratch folder and let Playwright serve them for the blocked CDN URLs with `context.route` (every `gstatic` URL can re-export one single bundle so there is only one SDK instance). Keep that scratch setup out of the repository.

## Roadmap

Work proceeds phase by phase, one commit series per phase. Before each phase, describe what will be done and get the owner's approval. Decisions that change behavior or architecture are proposed to the owner first (recommendation + reason), never made silently.

- [x] **Phase 0 - Foundation:** `shared/` folder, config example, emulator setup, this file.
- [x] **Phase 1 - Security:** username/password login (Firebase Auth, single admin), Firestore and Storage rules with validation, XSS fixes, upload limits.
- [ ] **Phase 2 - Correctness:** pure date/stock/discount functions with `node:test` tests, error handling, fix `priceLastUpdate` (only change when the price changes), discount settings in one config.
- [ ] **Phase 3 - Structure:** remove inline `onclick` handlers and `window.*` assignments, separate the customer page from admin code.
- [ ] **Phase 4 - UI:** responsive admin, QR download/print and a "site address" field (so QR codes work on a LAN), toasts and loading states, accessibility, image downscaling, TR/EN.
- [ ] **Phase 5 - Quality:** ESLint/Prettier, rules tests against the emulator, README and screenshots.

## Known issues being worked on

See the roadmap above. The most important ones now: expiry date maths mixes UTC and local time, `priceLastUpdate` changes on every save, and the QR code base URL is hard-coded in `admin/admin_script.js`.
